## 2. 题型识别矩阵

`detectType(node)` 按 `type` 属性优先、DOM 结构兜底的顺序判定：

| WJX `type` | 内部类型 | 支持 | 填写方式 |
|---|---|---|---|
| 1 / 2 | `text` | ✅ | 按 `verify` 生成（数字/手机/身份证/邮箱/文本） |
| 3 | `radio` | ✅ | 加权随机点选；支持内嵌填空复合 |
| 4 | `checkbox` | ✅ | 按 `minvalue`/`maxvalue` 与权重多选 |
| 5 | `rating` | ✅ | 星级点选 |
| 6 | `matrix` | ✅ | 逐行点 `a.rate-off`→`rate-on` |
| 7 | `dropdown` | ✅ | `select` 赋值 + `change` |
| 8 | `slide` | ✅ | 区间内随机 + `input`/`change` |
| 9 / `gapfill=1` | `gapfill` | ✅ | `span.textCont` 写回前一 `input.value` |
| 11 | `sorting` | ✅ | 按点击顺序落位，遵循配额 |
| 12 / `total` | `proportion` | ✅ | 按 `total` 分配并补取整误差 |
| — | `location` | ✅ | 地区弹层 |
| — | `unknown` | ⚠️ 跳过 | 面板提示，不静默填错 |

**识别判据的可靠性**：`verify` 属性优先于 `input type`。这是 0.1.16 修的核心问题——度数题 `verify='数字'` 但 `type='tel'`，只看 `type` 会写成 11 位手机号。

## 4. 状态与持久化

| 键 | 内容 | 生命周期 |
|---|---|---|
| `WJX_CN_PANEL_<host><path>` | 题目配置（权重、候选、开关） | 长期，导入导出载体 |
| `WJX_REMAINING_COUNT` | 会话剩余份数 | 跨页/跨刷新 |
| `WJX_AUTOMATION_STOPPED` | 停止标志 | 置位后阻止续跑，预览入口复位 |
| `WJX_COUNT_QUOTA_STATE` | 配额消耗 | 失败时由 `withQuotaRollback` 回滚 |

存储键按 host+path 归一化（非字母数字→`_`），同一站点不同问卷互不干扰。

## 5. 审计发现的问题

按严重度排列。**均已修复并附回归测试**。

### P1 · 内嵌填空写不进答案表（已修，0.1.19）
- **现象**：复合题界面有值，提交仍判「未作答」。
- **根因**：只派发 `input`/`change`，而问卷星绑的是 `blur keyup`；`keyup` 走 `otherTextEvent` 同步选项对象，`blur` 才 `saveAnswer`。
- **修法**：统一复用 `writeTextInput`。
- **验证**：反向验证——回退该行后集成测试立刻报 `inlineValue: null`，测试确实能抓住此缺陷。

### P1 · 调用点忽略写入结果（已修，0.1.19）
- **现象**：内嵌框写失败时无任何提示，面板看起来一切正常。
- **修法**：两处调用点检查返回值，失败走 `logWarning`。

### P2 · 配额回滚静默失败（已修，0.1.19）
- **现象**：`withQuotaRollback` 的空 `catch` 吞掉读取/恢复异常，份数可能凭空减少。
- **修法**：改 `logWarning`。`try/finally` 本身是正确用法，予以保留。

### P2 · `distributeRatiosToTotal` 合计不等于目标（已修）
- `(5, 1)` 返回合计 5 而非 1：`target` 被下限抬到项数、每项又被下限抬到 1。
- 修后 720 组（1–8 项 × 0–40 合计）不变量全成立。

### P2 · `distributeCountsEvenly` 零项陷阱（已修）
- `(0, 10)` 返回 `[10]`，给"不存在的第 1 项"分配全部次数。
- 修后返回 `[]`。

### P3 · 死字段 `optionTexts`（已清理，0.1.19）
- 只声明从不读写；真正的字段是 `optionFills`。

### P3 · 重复的可见性函数（已清理）
- `isNodeVisible` 与 `isElementVisible` 两份逐字节相同的副本，合并为一份定义 + 别名。

### P3 · 两语句挤在同一行（已清理）
- 2846 行 `const values = ...;            card.querySelectorAll(...)` 拆分。

## 6. try-catch 审计

审计时（v0.1.19）逐条分类了 45 处 `try {`（用户明确要求：不得用大量 `try-catch` 掩盖真实错误）。2.0.1 起脚本内实际为 **44 处 `try`（39 `catch` + 6 `finally`）**：新增的 1 处是清除本地数据后补删存档，另有 2 处随代码合并（`injectStyles` 幂等化、`getMatrixRowIndexBase`）并入既有分支。

| 所在函数 | 数量 | 处置 |
|---|---|---|
| `logWarning` 的 `console.warn` 兜底 | 1 | 保留。控制台不可用时无处可报 |
| `init` | 1 | 保留。初始化失败降级为不渲染面板 |
| 自动化会话状态读写（`loadAutomationSession` / `parseHostFromUrl` / `saveAutomationSession` / `isAutomationAborted` / `markAutomationStopped` / `clearAutomationStoppedFlag`） | 6 | 保留。`sessionStorage` 被禁用时用内存态 |
| 配置读写（`loadConfig` / `saveConfig` / `importConfigFromFile`） | 3 | 保留。失败已 `setSaveStatus` + `logWarning` 上报 |
| 配额读写与快照（`loadQuotaState` / `saveQuotaState` / `captureAttemptQuotaSnapshot` / `restoreAttemptQuotaSnapshot`） | 4 | 保留机制，空 `catch` 已改 `logWarning` |
| 设备残留清理（`clearSurveyDeviceState` / `clearCurrentSurveyStorage`） | 4 | 保留。单条 Cookie 清理失败不中断其余 |
| 面板事件绑定与显隐（`bindEvents` / `hidePanelForAutomation` / `showPanelAfterAutomation`） | 6 | 保留。含 4 处 `try/finally` |
| 重扫调度（`scheduleRescan`） | 1 | 保留 |
| 排序题交互（`clearSortingItems` / `applySortingItemState`） | 5 | 保留。点击与状态写回均有主路径兜底 |
| 页面按钮与翻页（`clickActionButton` / `dispatchTouchLikeEvent` / `triggerNativeNextPage`） | 5 | 保留。兼容旧浏览器缺失 API |
| 事件目标收集（`collectEventTargets`） | 8 | 保留。含 2 处 `try/finally` |
| **合计** | **44** | **0 处仍在静默吞掉有意义的错误** |

关键判断：**"有 try-catch" 本身不是缺陷**。缺陷是 catch 里既不上报也不降级。本次把唯一属于后者的一处（配额回滚）改为上报。

## 7. 性能审计

真实 Chrome，每轮全新页面，交替执行顺序，取中位数：

| 题数 | 本项目 | 上游原版 | 比值 |
|---|---|---|---|
| 7 | 18 ms | 9.3 ms | 1.94x |
| 27 | 22.2 ms | 13.1 ms | 1.69x |
| 67 | 32.4 ms | 20.1 ms | 1.61x |
| 147 | 55.6 ms | 33.6 ms | 1.65x |

**结论：斜率接近线性，倍率稳定在 1.6–1.9x，不存在随题数恶化的复杂度问题。** 147 题 55.6 ms 属于可接受范围。

> ⚠️ **本节数据已被 0.1.20 取代。** 上面这组测量来自 0.1.19，且当时 `tests/scale.test.js` 的 `repeatRadio` 用双引号做属性替换（WJX 导出 HTML 是单引号），140 份复制块的题号全是 `6`，「147 题」实际是「148 个同题号 DOM 块」，题数标签也少算 1（基础 fixture 是 8 题）。修正后 0.1.20 的重测结果见《测试报告》6.1：8 题 21.4 ms / 148 题 31.4 ms，上游 9.8 / 40.5 ms，148 题时本项目更快。本节的定性结论（近线性、无复杂度问题）仍然成立。

DOM 增量 355 vs 207（8 题场景）。逐节点核对后确认差异来源：**31 个功能按钮**（每张题卡 4 个快捷操作：随机比例 / 恢复本题 / 复制到同类题 / 暂不自动填写，上游仅 10 个按钮无卡片级操作；0.1.20 起全局按钮为 15 个，8 题 fixture 实测总按钮数 47）、66 个 DIV、19 个 OPTION（题型筛选器 16 项含「全部题型」 vs 上游 3 项）。**这些是功能密度差异，不是冗余，不予精简。**

空闲 1.5 s 后节点增长为 0，无 DOM 泄漏。

## 8. 安全与合规

- `@antifeature 自动批量提交`、`@antifeature 生成式随机答案可能造成低质量或重复回答` —— 已在脚本头显式声明。
- 风控识别：连续 2 次未通过人机验证即自动暂停并提示换网络，**不尝试绕过验证码**。
- 保留用户确认环节：默认流程为「填写到提交前暂停」，提交需用户确认；预览模式完全不提交。
- 外链（题库、QQ 群）需用户主动点击，不传递问卷内容或本地配置。
- 许可证 MIT，与上游一致；脚本头保留 `@original-author` / `@original-script` 溯源。

## 9. 结论

脚本功能完整、分层清晰，**未发现架构级缺陷**。本次审计修复了 2 个 P1（内嵌填空写不进答案表、静默失败）、2 个 P2（配额回滚静默失败、分配算法取整错误）、1 个 P2 边界陷阱，清理了 3 处死代码/重复代码。所有修复均有真实浏览器回归测试覆盖，其中内嵌填空修复做了反向验证以证明测试有效性。

**未重构任何已稳定运行的模块**，符合"不要随意重写已经稳定运行的模块"的约束。
