# 后续优化建议

> 排序依据：收益 ÷ 成本。**不含「为了显得有规划」而列的空项。**

---

## 第一优先：补齐验证覆盖（不是加功能）

**理由**：本次审计最真实的短板不是功能缺失，而是 12 项未验证（见《测试报告》第 7 节）。功能再多，没验证等于不知道能不能用。

### 1.1 建立真实题型样本库
- **做法**：在**获授权的测试问卷**中，为每种题型各建一题（含排序、占比、地区、滑块、评分、填空组、复合题），保存页面 HTML 到 `_debug/`，扩充 `tests/fixture.js`。
- **收益**：把当前「未验证」的 7 个题型一次性变成可回归。
- **成本**：低（一次采集，长期复用）。
- **风险**：无。纯测试资产。

### 1.2 手机版 fixture
- **做法**：采集 `v.wjx.cn` 的真实页面存档，单独建一套 fixture。
- **收益**：0.1.13 修的矩阵行差异可回归，不必依赖"当时看着对了"。
- **成本**：低。
- **风险**：无。

### 1.3 多页问卷 fixture
- **做法**：构造两页问卷，验证 `triggerNativeNextPage` 与跨页状态保持。
- **收益**：多页是高频场景，当前零覆盖。
- **成本**：中。
- **风险**：无。

## 第二优先：低风险的小改进

### 2.1 判断题标签识别
- **做法**：读 `.qtypetip` 文案 + 选项对特征（`正确/错误`、`对/错`、`√/×`），把 `type=3` 中明确是判断题的标为「判断题」。
- **前置条件**：**先取真实判断题样本验证判据**。纯文案匹配有误判风险（题干写「是否正确」但实际多选）。
- **收益**：仅面板显示更准，不影响填写。
- **成本**：低。
- **风险**：中（判据不准会造成误标）。**不满足前置条件就不做。**

### 2.2 配置失配提示
- **做法**：当配置里的题目在页面找不到匹配（题号+题型都对不上）时，面板顶部汇总提示「N 道题的配置未匹配到页面题目」。
- **收益**：问卷改版后用户能立刻发现问题，而不是提交了才发现填错。
- **成本**：低。
- **风险**：低。

## 第三优先：需要先有需求证据

### 3.1 分片渲染 / 虚拟滚动
- **现状（0.1.20 已实施）**：题目列表已改为**分页 + 列表内独立滚动**（默认 10 题/页，可选 10/20/50/200）。148 题时渲染 31.4 ms、上游 40.5 ms（7 轮中位数），渲染卡片数从 148 张降到恒定 10 张。
- **未做虚拟滚动的理由**：分页已消除「题目多就要一直往下翻」和「卡片数随题数线性增长」两个真实问题，且实现是「只渲染当前页」的整页替换，不涉及滚动过程中的增量 DOM 变更；虚拟滚动则需要维护滚动视口内的节点复用，风险显著高于收益。
- **触发条件**：只有当出现 **300 题以上**的真实问卷且用户仍反馈卡顿时才值得考虑。
- **风险**：高。虚拟滚动会引入状态同步 bug，可能破坏现有稳定的 DOM 扫描逻辑。
- **建议**：**不再做**，除非有实测卡顿证据。

### 3.2 多平台支持（腾讯问卷 / WPS 等）
- **现状**：调研显示 MingNin9466 用适配器模式覆盖 9 平台。
- **权衡**：本项目优势在「问卷星做深」（事件契约级正确性、可控分布），追平覆盖面等于放弃深度。
- **建议**：**不做**。除非用户明确提出跨平台需求。

## 明确反对的方向

| 方向 | 反对理由 |
|---|---|
| 加更多「智能随机」策略（如基于题干语义选答案） | 会显著提高「看起来像人填的」程度，加剧 `@antifeature 生成式随机答案` 的负面外部性。当前已声明该风险，不应主动加深 |
| 内置题库云端同步 | 涉及用户数据外传，与「不传递问卷内容或本地配置」设计冲突 |
| 破解复制限制 / 反检测 | 超出填写辅助范畴 |
| 用延时兜底异步时序 | 用户明确禁止。当前用「8 轮重扫 + 状态检测」，应保持 |
| 把现有 40 处 catch 大量改成 throw | 大部分是合理降级（存储失败用默认值）。改成 throw 会让面板在轻微异常下崩溃，是倒退 |

---

## 若只能做一件事

**做 1.1（真实题型样本库）。**

理由：本次修复的 4 个 P1 缺陷全部源自「代码逻辑与 WJX 真实契约不一致」——身份证校验位、填空事件链、内嵌填空事件链、填空组配置匹配。**每一类都可以被真实样本 fixture 提前发现。** 样本库是把"每次踩坑后补测试"变成"提前拦住"的唯一手段，且成本最低、零功能风险。

---

## 版本节奏建议

- **0.1.20**：仅做 1.1 + 1.2 + 1.3（纯测试资产 + 由此发现的 bug 修复），不引入新功能。
- **0.1.21**：2.2（配置失配提示）+ 若样本验证通过则含 2.1（判断题）。
- **之后**：进入维护态，只修真实环境反馈的 bug。

**不建议继续扩张功能面。** 当前 11 类题型已覆盖问卷星绝大多数场景，继续加功能的边际收益递减，而维护成本和出错面线性上升。脚本头的 `@antifeature` 声明也说明：这个工具的价值在于「可控、可核对的填写辅助」，不在于功能数量。
